## 1. 背景

OM（运维监控）原为基础设施层子系统，承载全系统可观测性（日志汇聚、指标时序、告警、运维看板）。其详细设计已明确：M-OM-01~04 实际职责是「只读查询/观测代理 + 分析入仓」，采集、存储、告警引擎、看板渲染本身由 **KubeSphere 底座**承担（OpenSearch / Prometheus / Alertmanager / Grafana）。

用户判断：**运维数据已由 KubeSphere 运维**，OM 的前端页面是重复造轮子，故删除 OM 运维监控部分；**业务数据计划落到各个子系统内**（各子系统自管自己的业务可观测性）。

OM 与 COM（公共功能）原**共用一个控制台**（运维管理控制台）：OM-01~05 为运维监控，OM-06~10 为 COM 的系统管理（用户/角色/组织/认证）。删 OM 须保留 COM。

## 2. 决策

### 决策 1：删除 OM 运维监控（OM-01~05），保留 COM 系统管理（OM-06~10）

- 删除 OM 运维监控部分：运维总览（OM-01）、日志检索（OM-02/03）、指标与告警（OM-04/05）共 5 页。
- 保留 COM 系统管理部分：用户管理（OM-06）、角色与权限（OM-07）、组织成员（OM-08）、登录策略（OM-09）、令牌与会话审计（OM-10）共 5 页。
- 理由：OM 的可观测能力已被 KubeSphere 覆盖，前端页重复；COM 的用户/角色/组织/认证是平台**不可缺失的刚需**（CON：权限/组织/认证），必须保留。

### 决策 2：原「运维管理控制台」改名为「系统管理」控制台

- 删 OM 后，原控制台只剩 COM 的 2 个菜单组（用户与组织、认证与会话）。
- 控制台品牌名「运维管理」→「系统管理」，顶栏代号「OM」→「系统」。
- 该控制台现为纯 COM 控制台（系统管理类页面，仅超级管理员可访问）。

### 决策 3：OM 删除只删线框，需求/模块留阶段二

- 与 ADR-001/002/003 策略一致。R-OM-001/002（2 项需求）、M-OM-01~04（4 模块）留阶段二评估。
- ⚠️ **接口链路风险**：各子系统向 OM 上报日志/指标的接口（II-04 日志上报、II-11 IRS 调用日志等）的去留，须连同"业务数据下沉各子系统"一起阶段二评估。

### 决策 4：「业务数据下沉各子系统」留阶段二

- 用户计划把 OM 原承载的业务可观测性（MC 执行网关动作日志、DC 采集健康度、IRS 推理调用日志等）下沉到各子系统自己的页面。
- 阶段一**不做下沉**，只做"删 OM + COM 独立"。下沉作为阶段二专项，需逐个子系统评估落点（如 MC-20 动作审计、MC-19 熔断监控已是 MC 自有的可观测页）。

## 5. 备选方案（已否决）

- **连 COM 一起删**：会失去用户/角色/组织/认证管理入口，平台无法运作。否决。
- **OM 连需求/模块一起废（阶段一）**：牵动各子系统向 OM 上报的接口链路（II-04 等）+ 业务数据下沉落点，是系统性问题。否决，留阶段二。
- **阶段一就做业务数据下沉**：下沉需逐个子系统评估落点，是一组独立设计决策，不能顺手做。否决，留阶段二专项。

## 6. 后果与风险

- **可观测性前端入口消失**：删 OM-01~05 后，全系统日志检索/指标看板/告警的前端入口没了。依赖 KubeSphere 原生控制台兜底，但 KubeSphere 控制台与本平台 UI 体验割裂。阶段二"业务数据下沉"须补齐各子系统的业务可观测入口。
- **接口孤儿风险**：II-04（日志上报）、II-11（IRS 调用日志）等原本各子系统→OM 的接口，删 OM 后失去消费方，阶段二须评估是废接口还是改向（如各子系统自管 + KubeSphere）。
- **OM 详细设计文档去留**：若阶段二废 OM 需求/模块，《软件详细设计说明-OM子系统.md》整份可能废止，是较大的文档动作。
- **控制台数量与命名**：原 4 控制台（OCC/MC/SWM/OM&COM），现 OM 部分删、COM 独立为「系统管理」，控制台仍 4 个（OCC/MC/SWM/系统管理），但语义边界变了。
- **阶段一/二不一致窗口持续扩大**：四批线框改动（SWM/MC/OCC/OM）全部完成，markdown 文档全旧。累计删页 18+5=23 页、术语全局替换、多处模块/需求/接口待评估。**强烈建议尽快启动阶段二**。
- **编号稳定**：R-OM-001/002、OM-01~10 编号本次不变（删的 OM-01~05 编号空置，OM-06~10 保留）。

## 1 引言

### 1.1 标识

本软件命名为"认知作战平台 v1.0"（以下简称"系统"或"平台"）。系统由三个相互协作的子系统组成：数据爬取子系统（DC）、多设备矩阵自动化群控子系统（MC）、运维监控子系统（OM）。本文件依据 GJB 438C 编制，给出系统的软件需求规格说明（SRS），作为概要设计、详细设计、开发实现与验收确认的依据。

> 说明：本文件为**对内**技术需求文件，如实描述系统各能力的真实用途与边界，供研发团队开发与验收使用。

### 1.2 软件概述

平台面向社交媒体，构建"数据采集 → 分析研判 → 编队执行 → 运维保障"的完整能力链。v1.0 由三大子系统构成：数据爬取子系统负责爬取工程底座、账号维护、社交媒体数据的采集与分析；多设备矩阵自动化群控子系统基于安卓设备矩阵，实现远程控制、群控、养号、数据兜底与内容投放，并对每一个动作提供可观测性；运维监控子系统汇聚多系统日志与指标，完成常态化运维。

三个子系统之间存在耦合关系。账号是数据爬取子系统与群控子系统的共享资产：数据爬取侧负责账号的注册、验证与风险评估，群控侧通过养号维持账号存活，并通过设备矩阵执行内容投放。群控子系统的移动端与网页端同时承担数据兜底采集的职能，作为常规爬取的补充手段。三个子系统均向运维监控子系统上报日志与指标。

### 1.3 文档概述

本文件第 1 章给出标识、概述与术语；第 2 章列出引用文件；第 3 章给出功能与非功能需求，其中功能需求按子系统划分为能力，每个能力以"能力说明、输入、处理、输出"段落式描述并附带需求编号；第 4 章规定合格性验证方法；第 5 章给出需求可追溯性；第 6 章为附录。功能需求编号采用 `FR-XX-NNN`（XX 为子系统代号 DC/MC/OM/COM），非功能需求编号采用 `NFR-类-N`，便于需求追踪与测试覆盖。

### 1.4 术语和缩略语

本节给出文档中使用的术语与缩略语。群控，指对多台移动设备进行集中、同步、批量控制。智能体控制，指在设备端部署 Agent，按服务端下发的策略自主执行任务。养号，指通过模拟真人行为（发帖、关注、浏览等）维持社交账号的活跃度与可信度。数据兜底，指在常规爬取不可达时，由移动端或网页端作为补充采集手段。逆向，指对目标 App 的网络协议或界面结构进行分析，以获取数据或实现自动化。风控，指社交平台对异常或自动化行为的检测与处置机制。设备指纹，指标识设备身份的硬件与软件特征集合。云手机，指云端虚拟化或容器化的安卓实例。ARM 板卡，指集成 ARM 芯片的安卓主板设备。Agent，指部署在终端设备上、与服务端通信并执行指令的代理程序。ADB，即 Android Debug Bridge，安卓调试桥。WebRTC，指支持实时音视频通信的协议，用于远程控制画面传输。ETL，即数据抽取-转换-加载。RBAC，即基于角色的访问控制。K8s，即 Kubernetes 容器编排平台。Kafka、Redis、HBase、Spark 分别为消息中间件、缓存与键值存储、列式数据库与分布式计算引擎。

## 3 需求

### 3.1 软件功能需求

软件功能需求按子系统组织。3.1.1 给出数据爬取子系统（DC）的功能需求，3.1.2 给出多设备矩阵自动化群控子系统（MC）的功能需求，3.1.3 给出运维监控子系统（OM）的功能需求，3.1.4 给出跨子系统的公共功能（COM）需求。每个能力以段落式描述其能力说明、输入、处理与输出，并给出需求编号以便追踪。

#### 3.1.1 数据爬取子系统（DC）

##### 3.1.1.1 爬取工程基础（FR-DC-001 ~ 004）

该能力为数据爬取子系统提供分布式运行的工程底座。能力说明：系统应提供可弹性伸缩的爬虫集群、可靠的数据流转通道、任务调度与去重机制，以及面向海外社交平台的代理网络出口，支撑后续采集、分析等能力的稳定运行。

输入包括爬虫任务定义（目标平台、采集范围、频率）、节点资源配置、代理 IP 与 VPS 代理链路配置，以及平台与地区的分配策略。

处理上，爬虫基于 K8s 部署，以容器化方式运行并支持横向扩缩容与节点自愈；采集到的原始数据经 Kafka 消息中间件流转，支持分区分组与回溯消费；任务调度与去重使用 Redis 实现，包括 URL 与任务去重、调度队列与分布式锁；代理 IP 池对接 VPS 代理链路，按平台与地区分配代理，定时轮换，并对代理进行可用性检测与失效剔除。

输出为运行中的爬虫实例、Kafka 中的原始数据流、调度指令与去重结果，以及可用的代理 IP 列表与轮换日志。

##### 3.1.1.2 账号维护（FR-DC-010 ~ 014）

该能力负责社交媒体账号的提交、验证、日常维护、注册与生命周期管理，是数据采集与群控执行的共享账号来源。

输入包括待提交的账号信息（平台、账号名、凭据、标签、归属）、平台注册方式（邮箱、手机接码、虚拟号）、维护任务（发帖、关注、浏览），以及账号状态变更事件。

处理上，账号提交后凭据加密存储并记录归属与标签；账号验证通过登录探测与状态识别检测账号是否可用，并识别封禁、限制、需要验证等风险点，输出风险等级；账号日常维护按拟人化的节奏模拟发帖、关注、浏览等真人行为，维持账号活跃度与权重；账号注册支持邮箱注册、手机号接码注册与虚拟号注册流程；账号生命周期在待登录、正常、受限、需验证、封禁、归档等状态间流转。

输出为入库的账号记录、账号可用性与风险评估结果、维护执行记录、注册成功的账号，以及账号的最新状态。

##### 3.1.1.3 社交媒体数据采集（FR-DC-020）

该能力从目标社交平台采集原始数据。能力说明：系统应支持多种采集手段，覆盖 TikTok、Instagram、Facebook、YouTube、X 等海外社交平台，作为后续分析的数据来源。

输入为目标平台标识与采集任务（采集对象、范围、频率、使用的采集方式）。

处理上，系统综合运用多种采集手段：对 Instagram 采用逆向方式采集推荐、人物、Reels 等界面数据；对 TikTok、Facebook 采用模拟点击自动化采集；对提供官方 API 的平台通过 API 授权采集；对网页端采用页面解析采集。采集过程中使用代理 IP 与维护账号，以应对平台访问限制。

输出为采集到的原始社交数据，包括用户信息、内容、互动数据、关系数据等。

##### 3.1.1.4 数据处理与存储（FR-DC-021 ~ 022）

该能力对原始数据进行清洗加工并持久化存储。能力说明：系统应提供标准的大数据 ETL 链路，完成数据的抽取、转换与加载。

输入为采集到的原始数据。

处理上，系统基于 Spark 或 MapReduce 进行分布式批处理计算，完成数据清洗、字段提取、格式标准化、去重与关联；处理结果写入 HBase 列式数据库，元数据与索引写入关系型数据库，关系数据写入图数据库。

输出为清洗加工后的结构化数据，持久化于 HBase 与关系库中，可供分析与检索使用。

##### 3.1.1.5 数据分析与情报（FR-DC-023 ~ 029）

该能力对加工后的数据进行分析，提供从群体到个体的筛选、关系图谱、情报检索与可视化，并支持文本智能分析。

输入为加工后的数据、群体特征条件、实体标识、检索条件，以及待分析的文本内容与关键词库。

处理上，系统结合人工智能算法实现从群体到个体的逐层下钻筛选，从大范围群体中定位目标个体；基于实体与关联数据绘制关系图谱并支持图查询；提供基础信息检索，按账号、昵称、标识等检索实体信息；对给定实体输出关联拓扑与情报标签，形成关联网络；聚合多来源信息形成实体的全维度档案；对文本内容结合文本模型与关键词库进行规则匹配与分类筛选，用于内容研判与目标识别。

输出为目标个体集合、关系图谱、实体信息列表、关联拓扑与情报信息、实体档案视图、文本分类与筛选结果，以及可视化展示界面。

#### 3.1.2 多设备矩阵自动化群控子系统（MC）

本子系统以开发方案 V1.1 为依据展开，并按对内真实用途补充执行目标（群控、养号、数据兜底、内容投放）。子系统的核心要求是集群控制具备可观测性，对每一个动作都能知晓与追溯。

##### 3.1.2.1 设备管理（FR-MC-001 ~ 007）

该能力管理多类型设备的接入、分组、状态监控与基础操作。能力说明：系统应统一管理云手机、ARM 板卡、真实安卓手机与安卓模拟器，并支持网页端接入，为后续的远控、群控与任务执行提供设备资源池。

输入包括设备标识与 Agent 信息、分组与标签规则、设备指标心跳，以及针对设备集合的批量操作指令。

处理上，Agent 启动后向服务端注册并建立长连接，系统记录设备类型（区分虚拟移动端与实体移动端）、版本、型号、分组与标签；系统持续采集并监控设备的在线与离线状态、电量、CPU、内存、存储与网络状态；系统支持网页端接入，用于数据兜底获取与养号；系统支持对设备集合进行批量安装与卸载 App、批量重启、批量截图，以及通过对象存储临时链接进行文件上传与下载。

输出为设备台账、设备分组关系、设备实时状态视图，以及批量操作执行结果。

##### 3.1.2.2 远程控制（FR-MC-010 ~ 014）

该能力提供对单台及多台设备的实时远程控制。能力说明：系统应提供低延迟的设备画面预览与输入控制，并支持多设备同屏监控，用于人工介入与设备操作。

输入为远控请求、目标设备标识，以及操作人员的鼠标、键盘输入事件。

处理上，屏幕画面基于 WebRTC 传输，远程控制通道与任务执行通道相互分离以保证稳定性；操作人员的鼠标与键盘事件被映射为设备的触摸、点击、滑动、输入及返回键、Home 键、多任务键事件；系统支持由 Agent 采集的截图与录屏，并支持保存与回看；多设备宫格监控以低码率同屏预览多台设备；剪贴板在操作端与设备间双向同步。

输出为设备的实时画面流、被翻译并执行的设备事件、截图与录屏文件，以及多设备宫格预览画面。

##### 3.1.2.3 群控与执行（FR-MC-020 ~ 024）

该能力是群控子系统的核心执行能力，实现两种控制模式及其四类执行目标。

输入包括控制指令或任务策略、目标设备组、内容素材，以及目标账号与设备。

处理上，手机群控模式接收控制指令与设备组，对多台设备进行同步控制，统一投放内容；手机智能体控制模式由设备端 Agent 按服务端下发的策略自主执行任务，适应更复杂的执行场景；数据兜底获取由移动端与网页端作为常规爬取的补充手段执行采集任务；养号通过移动端按拟人化节奏模拟发帖、关注、浏览等真人行为，维持账号的活跃度与权重；内容投放下发并发布内容素材到目标社交平台的目标账号。所有执行动作均纳入可观测性体系留痕。

输出为群控同步执行结果、智能体自主执行结果、兜底采集数据、养号执行记录，以及内容投放执行记录。

##### 3.1.2.4 账号管理（FR-MC-030 ~ 032）

该能力在群控侧管理账号与设备、登录状态及操作记录，复用数据爬取子系统维护的账号池。

输入为账号与设备的绑定关系、账号登录事件，以及账号操作（发帖、关注、浏览等）。

处理上，系统将账号绑定到具体设备，记录绑定关系；系统记录账号在设备上的登录状态及其变化；系统记录账号的各项操作，供审计与风控分析使用。

输出为账号与设备的绑定关系、登录状态记录，以及账号操作记录。

##### 3.1.2.5 内容管理（FR-MC-040 ~ 042）

该能力管理投放所需的内容素材、发布排期与发布审核。

输入为图片、视频、文案等素材，素材的标签与平台分类信息，发布排期，以及待发布内容。

处理上，系统对素材进行分类管理，支持标签、平台分类与账号适配；系统支持按素材、账号与时间制定定时发布排期；发布前对内容进行审核与敏感词检测。

输出为素材记录、发布排期，以及内容审核结果。

##### 3.1.2.6 任务管理（FR-MC-050 ~ 054）

该能力把操作意图转换为设备可执行的任务并进行调度。

输入为任务定义（任务类型、目标设备或设备组、参数、优先级）、计划任务的 Cron 表达式，以及任务状态变更事件。

处理上，系统按任务定义选择设备或设备组，生成任务实例并入消息队列，由调度器分发到设备 Agent 执行；系统支持的任务类型包括 App 安装与启动、文件分发、内容发布、截图、数据采集、自动化脚本、设备巡检与账号状态检查；任务在待执行、排队中、执行中、成功、失败、已取消、超时、部分成功等状态间流转；系统支持失败重试、重试次数与超时配置；计划任务支持一次性、每日、每周与自定义 Cron，并支持最大并发数与任务优先级控制。

输出为任务实例、任务调度分发结果、任务执行结果与任务最新状态。

##### 3.1.2.7 自动化脚本与工作流（FR-MC-060 ~ 063）

该能力提供从模板任务到可视化工作流再到脚本开发的递进式自动化能力。

输入为模板任务选择、工作流流程定义、脚本代码与调试设备，以及平台界面与操作序列。

处理上，第一阶段提供模板化任务，包括打开 App、等待页面、点击、输入文本、上传文件、截图、返回、滑动、关闭 App、设备巡检与 App 状态检测；第二阶段提供可视化工作流编排，节点包括开始、设备选择、启动 App、等待、点击、输入、滑动、截图、文件上传、条件判断、循环、HTTP 请求、日志、审批与结束；第三阶段支持脚本开发与调试，提供脚本编辑、调试设备、执行日志、截图回放与版本管理；此外，系统针对 TikTok、Facebook 等平台实现模拟点击自动化。

输出为模板任务执行结果、工作流执行编排结果、脚本调试结果，以及模拟点击自动化执行结果。

##### 3.1.2.8 可观测性（FR-MC-070 ~ 073）

该能力满足集群控制对可观测性的硬性要求，使每一个动作都可知、可追溯。能力说明：系统应对设备、账号、任务的每一个动作进行记录、回传、告警与审计。

输入为设备动作事件、任务执行过程、异常事件，以及用户与系统的操作。

处理上，每一个设备动作（点击、输入、安装、发布等）均留痕，记录时间、设备、账号与结果；Agent 回传任务执行日志与关键步骤截图；任务失败、设备掉线、账号异常等异常事件触发告警通知；系统对用户与系统操作记录审计日志，记录谁在何时对哪台设备或账号做了什么。

输出为动作日志、任务执行日志与截图、异常告警通知，以及可追溯的审计记录。

##### 3.1.2.9 设备环境与风控对抗（FR-MC-080 ~ 083）

该能力管理设备环境并应对平台风控，以降低账号与设备被处置的风险。

输入为设备环境参数、风控信号、代理分配策略，以及设备集合的隔离要求。

处理上，系统管理设备的硬件与软件指纹，支持按需配置；系统识别平台风控信号并采取规避与应对策略；系统为设备分配独立代理 IP 以实现网络环境隔离；系统对设备间的环境（指纹、网络、账号）进行相互隔离，避免关联。

输出为设备的指纹配置、风控规避策略、代理绑定关系，以及设备环境隔离配置。

#### 3.1.3 运维监控子系统（OM）

##### 3.1.3.1 日志与指标汇聚（FR-OM-001 ~ 002）

该能力汇聚多系统日志与指标。能力说明：系统应汇聚数据爬取子系统、群控子系统及平台自身的日志与指标，形成统一的运维数据底座。

输入为各子系统产生的日志与系统运行指标。

处理上，系统通过日志采集将各子系统日志汇聚至统一日志库，支持全文检索；系统通过指标采集器采集设备在线率、任务成功率、爬虫吞吐量、队列积压等指标，形成时序数据。

输出为统一日志库与时序指标数据。

##### 3.1.3.2 告警与运维（FR-OM-003 ~ 005）

该能力提供告警管理与常态化运维。能力说明：系统应基于指标与规则产生告警，并通过仪表盘与运维操作支持日常运维。

输入为告警规则与指标、运维操作请求。

处理上，系统支持阈值告警与异常检测告警，并通过多渠道通知；系统提供总览、设备、任务、爬虫、异常等多维可视化看板；系统支持日志查询、故障定位、巡检与容量观测等常态化运维操作。

输出为告警事件、可视化看板，以及运维操作记录。

#### 3.1.4 公共功能（COM）

##### 3.1.4.1 用户认证与权限（FR-COM-001 ~ 003）

该能力提供跨子系统的用户认证、权限控制与组织管理。能力说明：系统应提供统一登录与基于角色的访问控制，并支持多组织的数据隔离。

输入为用户账号与密码或双因素凭证、角色与权限配置、组织与成员信息。

处理上，系统进行登录认证并支持双因素；系统基于角色的访问控制进行权限决策，角色包括超级管理员、运营主管、运营人员、脚本开发者、审核人员与只读观察员等；系统对多组织或多租户进行数据隔离。

输出为认证令牌、权限决策结果，以及组织结构。

### 3.2 外部接口需求

系统应提供与外部系统交互的接口。其一，系统应通过逆向、模拟点击与官方 API 等方式与 TikTok、Instagram、Facebook、YouTube、X 等社交平台交互（EI-01）。其二，系统应对接 VPS 代理链路与代理 IP 供应商，获取代理网络出口（EI-02）。其三，系统应对接手机号接码与虚拟号服务，用于账号注册（EI-03）。其四，系统应对接第三方云手机供应商 API，获取云手机实例（EI-04）。其五，系统应对接 MinIO 或阿里云 OSS 等对象存储，存储素材、截图与录屏（EI-05）。其六，系统应对接 AI 模型服务，用于文本智能分析（EI-06）。所有外部接口均应使用鉴权与传输加密。

### 3.3 内部接口需求

子系统间及子系统内部应通过明确的接口交互。数据爬取子系统与群控子系统之间应提供账号池接口，群控子系统据此复用账号并绑定设备（II-01）。群控子系统的 Agent 与服务端之间应通过 WebSocket 或 MQTT 长连接下发指令并回传日志（II-02）。群控子系统与设备之间应通过 WebRTC SFU 传输远控画面与输入（II-03）。各子系统应通过日志采集 Agent 与指标采集器向运维监控子系统上报日志与指标（II-04）。数据爬取子系统内部应以 Kafka 作为数据总线，将采集数据流转至处理与存储环节（II-05）。系统应提供设备、任务、内容、账号、审计等管理的 REST 接口，供前端与外部调用（II-06）。

### 3.4 数据需求

系统应维护以下数据：设备数据，包括设备、设备分组与设备指标（DR-01）；账号数据，包括社交账号、登录记录与操作记录，凭据须加密存储（DR-02）；内容数据，包括素材、发布排期与发布记录（DR-03）；任务数据，包括任务、任务实例与任务日志（DR-04）；脚本与工作流数据，包括脚本、脚本版本与工作流定义（DR-05）；采集与分析数据，其中 ETL 结果存于 HBase，关系数据存于图数据库（DR-06）；审计与风险数据，包括审计日志与风险事件（DR-07）；代理与指纹数据，包括代理 IP 池与设备指纹配置（DR-08）。

### 3.5 性能需求

系统应满足以下性能要求。单设备远程控制端到端延迟应不大于 300 毫秒，多设备宫格预览可适当放宽（NFR-P-01）。单租户应支持不少于 200 台设备的并发接入与控制（NFR-P-02）。数据爬取子系统的爬虫集群应满足业务采集量的日处理能力，并支持水平扩展（NFR-P-03）。任务从入队到分发应不超过 2 秒，并支持任务优先级与最大并发控制（NFR-P-04）。WebRTC SFU 应支持单节点并发多路远控流，并在弱网下自动降帧（NFR-P-05）。运维监控的日志检索响应应不超过 3 秒，覆盖近 7 日数据（NFR-P-06）。

### 3.6 安全性需求

系统应满足以下安全性要求。系统应提供用户认证与双因素，并对全部 API 进行鉴权（NFR-S-01）。系统传输应全程使用 HTTPS 或 TLS，远程控制通道应加密（NFR-S-02）。账号凭据、代理凭据等敏感字段应加密存储，不得明文落库（NFR-S-03）。Agent 应进行签名校验以防止伪造设备接入，指令应签名（NFR-S-04）。脚本应运行于沙箱并配置权限白名单，禁止越权访问与读取敏感路径（NFR-S-05）。所有账号、设备、任务操作应留存审计日志，可追溯（NFR-S-06）。文件访问应使用签名 URL，限时有效（NFR-S-07）。

### 3.7 保密性需求

系统应满足以下保密性要求。多组织或多租户的数据应严格隔离，禁止跨组织访问（NFR-C-01）。数据访问应遵循最小权限原则，按角色与数据范围控制（NFR-C-02）。手机号、凭据等敏感数据应脱敏展示（NFR-C-03）。数据库应定期备份，数据导出操作应审计留痕（NFR-C-04）。

### 3.8 可靠性需求

系统应满足以下可靠性要求。核心服务可用性应不低于 99.5%（NFR-R-01）。任务应支持幂等与失败重试，异常任务应自动熔断（NFR-R-02）。Agent 掉线应自动重连，设备重启后 Agent 应自启动（NFR-R-03）。关键服务应高可用部署，无单点故障（NFR-R-04）。数据采集应具备补偿与断点续采能力（NFR-R-05）。

### 3.9 可维护性需求

系统应满足以下可维护性要求。系统应采用模块化、服务化设计，子系统可独立部署升级（NFR-M-01）。采集、调度、频率控制、代理等关键策略应可配置，无需修改代码（NFR-M-02）。系统应提供全链路日志与追踪，故障可定位（NFR-M-03）。系统应提供运维仪表盘与告警，支持常态化运维（NFR-M-04）。

### 3.10 易用性需求

系统应满足以下易用性要求。Web 管理后台界面应清晰，设备、任务、账号、内容分区明确（NFR-U-01）。批量操作应支持选择设备组并一键下发（NFR-U-02）。远程控制画面与任务日志应同屏可见（NFR-U-03）。关键操作应有确认与风险提示（NFR-U-04）。

### 3.11 运行环境需求

服务端应运行于 Linux 操作系统，采用 Docker 与 Kubernetes 进行容器编排，后端采用 Java Spring Boot 或 Go。数据存储应包括 PostgreSQL 或 MySQL、Redis、Kafka、HBase、图数据库与 MinIO 或 OSS。前端应基于现代浏览器，采用 Vue3 或 React 与 TypeScript。移动端应提供 Android Agent，兼容主流 Android 版本，设备类型包括云手机、ARM 板卡、真机与模拟器。监控应采用 Prometheus、Grafana 与 ELK 或 Loki。

### 3.12 故障处理需求

系统应满足以下故障处理要求。任务异常应自动熔断，停止后续执行并告警（NFR-F-01）。设备或 Agent 异常应自动隔离，不再派发任务，待恢复后重新接入（NFR-F-02）。账号发生封禁或受限等异常时，应自动停止该账号相关任务并告警（NFR-F-03）。消息中间件或数据库故障应具备重试与死信处理（NFR-F-04）。服务异常应具备降级能力，优先保障远程控制与日志通道（NFR-F-05）。

### 3.13 约束条件

群控子系统应按开发方案 V1.1 分阶段落地，最小可行产品优先接入云手机与真机、实现远程控制与基础任务（CON-01）。第一阶段不自研云手机内核，优先接入第三方云手机 API（CON-02）。爬虫与 ETL 应复用现有大数据组件，包括 Kafka、Spark 与 HBase（CON-03）。v2.0 的素材制作与战法库等能力本期不实现（CON-04）。目标平台为海外社交平台，需考虑网络代理与合规边界（CON-05）。

## 4 合格性规定

### 4.1 验证方法

系统应采用评审、演示、测试与分析相结合的方法进行合格性验证。评审用于对需求与设计文档进行相关方确认。演示用于对设备接入、远程控制、群控、采集与可视化等能力进行现场展示。测试用于对功能、接口、性能与安全进行验证。分析用于对日志、指标与审计记录进行分析确认。

### 4.2 验证条件

合格性验证应在部署完整的三大子系统及其依赖组件的测试环境中进行。环境应接入不少于规定数量的测试设备，包括云手机与真机，以及测试账号。应准备目标平台的测试数据与代理 IP 资源。

### 4.3 验证准则

验证应以本文件的需求为准则。功能需求应逐项验证通过。非功能需求应达标，其中性能指标应经实测满足，安全项应无高危问题。各子系统接口应联通，日志与指标应正常上报至运维监控子系统。验证应无遗留的致命与严重缺陷。

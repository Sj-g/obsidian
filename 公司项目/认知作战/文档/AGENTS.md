## 3. 编号体系（编辑文档时严格遵守）

编号是全文交叉引用与双向追溯的基石，改动需联动全文，不得随意。

| 对象 | 格式 | 示例 |
| --- | --- | --- |
| 功能需求 | `R-XX-NNN`（XX=子系统代号） | R-DC-001、R-OCC-006 |
| 非功能需求 | `NR-类-N`（类=S安全性/C保密/P性能/R可靠/M可维护/F故障） | NR-S-01 |
| 外部接口 | `EI-NN` | EI-05 |
| 内部接口 | `II-NN` | II-13 |
| 数据需求 | `DR-NN` | DR-06 |
| 约束条件 | `CON-NN` | CON-07（动作收口） |
| 软部件/模块 | `M-XX-NN`（M-XX-00 为子系统自身） | M-MC-00、M-DC-03 |
| 功能点 | `F-XX-NN-NN` | F-MC-05-01 |

**编号联动原则**：需求编号末位与对应模块 `M-XX-NN` 末位对齐，便于配置项管理与需求双向追溯。重排需求编号时（如 V3.2→V3.3 的 DC/OCC 重排），必须同步全文约 40+ 处交叉引用，并记录在版本变动记录中。

## 5. 核心设计原则（源自 CON-01~CON-13）

修订任何设计文档时，下列原则不可违背：

1. **动作收口（CON-07）**：所有执行终端动作（脚本/智能体、移动端 ADB/无障碍、桌面端 CDP）均经 MC 统一执行网关落地，禁止绕过，保证可观测、可审计、可熔断。
2. **推理与执行分离（CON-10）**：智能体视觉推理由 Agent 调 IRS 本地大模型完成，不经执行网关；动作指令再经网关落地。
3. **双执行模式（CON-08）**：脚本模式与智能体模式并存，共用底层控制通道，均收口于执行网关。
4. **权威源唯一（CON-11）**：账号主数据由 **MC** 唯一维护（R-MC-011）、内容主数据由 **OCC** 唯一维护；使用方只引用标识，变更经事件总线通知。
5. **私有化推理（CON-06）**：大模型私有化部署，不依赖外部公有云。
6. **可观测优先**：各子系统向 OM 上报日志与指标，关键动作全量留痕。
7. **作战单元**：移动端 `agent_id:account_id:终端:代理IP = 1:1:1:1`；移动端"一设备一账号一 IP"，桌面端"一 Profile 一账号一 IP"。
8. **统一技术栈分工**：**管控/业务微服务统一用 Java（Spring Boot）；数据采集与分析（爬虫采集 worker、PySpark ETL）用 Python；两者经 Kafka/REST 解耦。** DC 整体归 Python 为「采集域特例」（其 dc-service 管控面与 crawler/ETL 同属数据采集体系），不算违背原则；OM、COM 等其余管控/业务微服务用 Java。鉴权采用 JWT 无状态令牌 + com-auth-lib 共享验签库（各子系统本地验签，无网络开销）。

## 6. 文档编辑规范

### 6.1 通用
- 文档头部信息块（项目名称/版本/密级/编制/编制日期）格式统一，修订时更新版本号与日期。
- 章节编号沿用 GJB 438C 体系（`## 1`/`### 1.1`/`#### 1.1.1`）。
- 术语与缩略语沿用 SRS 第 1.4 节，关键术语：执行网关、执行模式、控制通道（ADB/无障碍/CDP）、指纹浏览器、浏览器 Profile、指纹固化、设备风控分级、权威源、主数据、扩展数据、事件通知、蜂群、人设标签、抓手、舆情对冲。
- 表格采用 Markdown，使用 Obsidian 兼容写法；图示用 `mermaid` 代码块。

### 6.2 多文档联动（改动牵连最广的坑）
需求/编号一旦变动，下列需同步对齐，否则追溯链断裂：
- `SRS/` 目录（SRS 源头：总册 + 7 子系统分册；改某子系统需求改对应分册，改共性章节改总册）
- `软件需求跟踪矩阵.xlsx`（RTM）
- `软件概要设计-模块功能拆分-v2.xlsx`
- `软件概要设计-架构图.md`
- `软件概要设计说明.md`
- `文档目录.md` 的"维护状态/版本"列

### 6.3 版本管理
- 每次实质性修订：①更新文档头部版本号与日期；②在 `版本变动记录/版本变动记录.md` 追加一条（版本/日期/修改文档/修改内容摘要/修改人=石建国）。
- 结构性调整（子系统增减、需求编号重排、接口方向变化）须在变动记录中给出**变更明细**（参照 V3.3 变更明细的写法：结构调整 / 编号重排 / 接口方向 / 需求数变化 / 交叉引用修正 / 同步对齐文档）。

### 6.5 需求跟踪的权威源（单一源，勿在文档中另设）

- 需求双向追溯（上游来源 → 需求 `R-XX-NNN` → 设计模块 `M-XX-NN` / 功能点 `F-XX-NN-NN` → 验证方法）的**唯一权威交付物**是 [`软件需求跟踪矩阵.xlsx`](./软件需求跟踪矩阵.xlsx)（RTM，GJB 438C，7 张工作表）。
- **不要**在 markdown 文档中为需求跟踪另设目录 / 章节 / 文件来重复维护明细追溯关系——单一权威源，避免双源失同步。
- 修订需求、模块、接口、数据、约束后，更新 xlsx 即完成追溯维护，不必同步改文档内追踪表。
- 文档（如概要设计）若需呈现追踪，只做**概要性引用**，明细一律以 xlsx 为准。

## 8. 常见任务模式

- **新增/修改一条需求**：改 SRS 对应子系统分册（`SRS/软件需求规格说明-XX子系统.md`，共性章节改 `SRS/软件需求规格说明-总册.md`）→ 重排编号（如触发）→ 同步模块拆分/架构图/概要设计 → **更新 `软件需求跟踪矩阵.xlsx`（追溯唯一权威源，见 6.5）** → 更新文档目录状态 → 追加版本变动记录。
- **校对全文一致性**：grep 编号（如 `R-DC-`、`M-MC-`、`II-1`）核对跨文档引用是否对齐当前版本。
- **回答项目问题**：优先以 SRS（需求真相）与概要设计说明（设计真相）为准；子系统职责以本文档第 4 节速查表为入口。

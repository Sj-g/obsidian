# 软件概要设计简述（认知作战 · 数据采集子系统）

> 本文档聚焦**数据爬取子系统**的概要设计，重点解决架构评审中识别的 **P0 级薄弱环节**：
> 1. 任务调度中心缺失
> 2. 监控告警体系缺失
> 3. 数据质量与去重机制缺失
>
> **采集模式采用「链接驱动」**：待爬链接由**外部程序 / 人工维护**注入「链接池」，
> 爬虫作为执行器消费链接池，拿到 URL 才去抓取——而非定时自动巡采。
>
> 底层架构沿用既有设计：**爬虫集群 + Kafka 消息中枢 + 多存储分库（PG / HBase / OSS / ES）**，
> 基础设施使用 **Rancher 管理 K3s**。

---

## 0. 系统总体定位

**核心范式：链接驱动采集（Pull from Link Pool）**

```mermaid
flowchart TB
    subgraph EXT["外部链接源（其他程序 / 人工维护）"]
        L1["人工分析选定目标 URL"]
        L2["侦察程序发现可疑链接"]
        L3["战法库定向下发目标"]
    end
    EXT -->|"注入链接"| LP[("链接池<br/>Link Pool<br/>入池即 URL 去重")]
    LP -->|"消费链接"| B["① 调度中心 P0新增<br/>按优先级分发"]
    A["设备维护服务<br/>账号池 / IP池 / Cookie池 / 设备指纹"] --> B
    B -->|"下发抓取任务"| C["爬虫集群 Pod<br/>（执行器：拿URL→抓内容）"]
    C --> K[("Kafka 集群")]
    K --> D["下载器 / ETL<br/>含 ③ 质量校验+去重"]
    K --> E["日志处理模块"]
    K --> F["② 监控采集 P0新增"]
    D --> P[("PostgreSQL/HBase<br/>元数据")]
    D --> O[("OSS<br/>多媒体 / 冷数据归档")]
    E --> ES[("Elasticsearch<br/>日志全文检索")]
    F --> M[("Prometheus + Grafana<br/>② 监控告警 P0")]
    F -.->|"链接池水位反馈"| LP
```

**设计原则：**
```text
1. 链接驱动：链接由外部维护并注入链接池，爬虫只消费、不主动发现
2. 调度编排：调度中心消费链接池，按优先级分发，禁止散落式定时器
3. 可观测优先：没有监控的模块不允许上线
4. 质量内建：去重与校验嵌入管道，脏数据不落库（入池去重 + 入库去重双层）
5. 弹性解耦：Kafka 作为唯一中枢，采集与处理彻底异步
```

## ① P0-1：链接池 + 调度中心设计

### 1.1 思路转变：链接驱动 vs 定时驱动

| 维度 | 定时驱动（原思路） | **链接驱动（采用）** |
|---|---|---|
| 触发方式 | Cron 定时巡采平台 | **外部注入链接 → 消费链接池** |
| 链接来源 | 爬虫自己发现/翻页 | **其他程序 / 人工维护** |
| 爬虫角色 | 主动探索者 | **被动执行器（拿 URL 抓内容）** |
| 资源消耗 | 大量浪费在无目标巡采 | **定向采集，资源精准投放** |
| 反爬风险 | 高（漫无目的易触发风控） | **低（有目的、可节制）** |
| 适用场景 | 全量舆情监测 | **认知战定向情报采集** ⭐ |

**采用链接驱动的理由：** 认知作战强调**定向、精准、可追溯**的情报采集，目标账号/帖子 URL 由分析师或侦察程序预先确定，爬虫无需（也不应）自行泛化探索。

### 1.2 链接池设计（核心新增组件）

链接池是整个系统的**输入闸门**，由外部程序/人工维护。

#### 链接数据结构

```text
link_pool
  - link_id            主键
  - url                待爬 URL
  - url_hash           URL 规范化后的哈希（入池去重键）
  - source_type        来源：manual（人工）/ recon（侦察程序）/ tactic（战法库）
  - source_ref         来源标识（如战法 ID、分析师账号）
  - platform           平台（TikTok / X / FB / TG ...）
  - priority           优先级（P0~P4，见 1.5）
  - status             状态：pending / claimed / done / failed / skipped
  - dedup_at_pool      入池时是否已去重
  - injected_at        入池时间
  - claimed_at         被调度领取时间
  - finished_at        完成时间
  - retry_count        重试次数
  - remark             备注（如采集意图）
```

#### 入池流程（含 URL 级去重）

```mermaid
flowchart LR
    IN["外部注入链接"] --> NORM["URL 规范化<br/>去参/统一域名/去片段"]
    NORM --> HASH["计算 url_hash"]
    HASH --> EXIST{"链接池已存在?"}
    EXIST -->|"是"| MERGE["合并优先级<br/>取更高值，更新备注"]
    EXIST -->|"否"| INSERT[("写入链接池<br/>status=pending")]
    MERGE --> INSERT
```

**URL 规范化规则（保证去重有效）：**
```text
1. 统一协议（http → https）
2. 域名小写
3. 去除跟踪参数（utm_*、fbclid、spm 等）
4. 去除 fragment（#后内容）
5. 路径去末尾斜杠
6. 排序 query 参数
```

#### 链接来源接入方式

```text
1. REST API：POST /api/links/batch  （人工/程序批量注入）
2. 战法库回调：战法执行时自动下发目标链接
3. 侦察程序推送：MQ/Kafka  topic=link-inject
4. 文件导入：CSV/Excel 批量导入（分析师常用）
```

### 1.3 技术选型

```text
链接池存储：PostgreSQL（结构化、可查询、可审计）+ Redis（待消费队列）
调度引擎：  Apache DolphinScheduler（消费链接池 → 编排分发）
任务队列：  Redis ZSet（按优先级）+ Kafka（分发到爬虫 Pod）
状态存储：  复用链接池表（status 字段驱动状态机）
```

### 1.4 调度模型

调度中心从"定时触发"转为"**消费链接池**"：

```mermaid
flowchart TB
    LP[("链接池<br/>status=pending")] --> POLL["调度轮询/事件触发<br/>（有新链接即消费）"]
    POLL --> FETCH["按优先级批量领取<br/>UPDATE status=claimed"]
    FETCH --> QUOTA{"配额/限流校验<br/>账号/IP 水位"}
    QUOTA -->|"不足"| WAIT["等待 / 降并发"]
    QUOTA -->|"充足"| DISP["任务分发器"]
    WAIT --> DISP
    DISP -->|"Kafka"| POD["爬虫 Pod"]
    POD -->|"抓取回报"| SM["状态机更新<br/>done / failed / retry"]
    SM -.->|"续爬/重试"| LP
    MON2["② 监控水位"] -.->|"反馈调节"| QUOTA
```

> **注：** Cron 定时仅用于一个轻量场景——**对已采集链接的周期性复查**（增量更新，如某帖子新评论）。主采集模式始终是链接驱动，不存在"定时全量巡采"。

### 1.5 链接优先级策略

优先级在**链接入池时**由来源决定，调度按权重消费：

```text
P0  战法库下发链接（指挥集群定向）         权重 100
P1  人工分析师标注高价值链接               权重 80
P2  侦察程序发现的可疑链接                 权重 60
P3  常规目标链接                           权重 40
P4  历史回溯 / 复查链接                     权重 20
```

### 1.6 任务（链接）状态机

```mermaid
stateDiagram-v2
    [*] --> pending: 外部注入
    pending --> claimed: 调度领取
    claimed --> running: Pod 开始抓取
    running --> done: 抓取成功
    running --> failed: 抓取失败
    running --> timeout: 超时
    failed --> retry: 重试 ≤ 3
    timeout --> retry: 重试 ≤ 3
    retry --> pending: 回池重排
    retry --> dead: 超限进死信
    pending --> skipped: 命中内容去重
    done --> [*]
    dead --> [*]
    skipped --> [*]
```

### 1.7 关键能力清单

```text
1. 链接池：外部 API/MQ/文件 多方式注入
2. 入池 URL 规范化去重（避免同一链接重复入池）
3. 优先级队列（抢占式调度，战法优先）
4. 配额限流（基于账号池/IP 池水位动态调节并发）
5. 断点续爬（链接 status 回 pending，重启续跑）
6. 失败重试（指数退避，最多 3 次，超限进死信）
7. 周期复查（Cron 仅复查已采链接增量，非全量巡采）
8. 链接审计（谁、何时、为何注入该链接，全程留痕）
```

## ② P0-2：监控告警体系设计

### 2.1 问题与目标

原架构**零监控**：链接池积压、账号池耗尽、Kafka 积压、爬虫被封、磁盘写满——全部要等业务投诉才能发现。对认知战场景，数据时效性与连续性是生命线，必须做到**分钟级感知**。

### 2.2 技术选型

```text
指标采集：Prometheus（Pull 模型）+ node_exporter / kafka_exporter / postgres_exporter
日志采集：Filebeat → Kafka → Logstash → Elasticsearch（复用现有 ES）
链路追踪：OpenTelemetry（链接级 trace，从入池到入库全链路）
可视化：  Grafana（大盘）+ Alertmanager（告警路由）
告警通道：企业微信 / 钉钉 / 电话语音（P0 级）
```

### 2.3 指标体系（系统指标 + 业务指标）

#### 系统指标（基础设施健康度）

```text
节点：CPU / 内存 / 磁盘 / 网络 IO / Pod 重启次数
Kafka：消费 Lag / 生产速率 / 分区均衡度 / ISR 缩减
存储：PG 连接数 / 慢查询 / HBase Region 热点 / ES Heap / OSS 写入速率
调度：链接池积压数 / 调度领取延迟 / 分发耗时
```

#### 业务指标（数据采集健康度）⭐ 认知战场景核心

```text
链接池侧（新增重点）：
  - 链接池水位（pending / claimed / done / failed 分布）
  - 链接注入速率（按来源：manual/recon/tactic 拆分）
  - 链接消费速率 / 消费延迟（入池→抓取完成）
  - 入池去重命中率（过高=重复注入，需提示来源方）

采集侧：
  - 各平台爬虫成功率 / 封禁率（4xx/5xx/验证码占比）
  - 账号池可用水位 / IP 池可用水位 / Cookie 失效率
  - 单平台 QPS

流转侧：
  - Kafka 端到端延迟（采集→入库）
  - ETL 处理吞吐 / 积压条数

质量侧：
  - 内容去重命中率（入库时，见 P0-3）
  - 数据质量校验失败率
  - 死信队列积压量

时效侧：
  - 链接入池→首条数据落地 时延（认知战 SLA：< 5 分钟）
```

### 2.4 告警分级与路由

| 级别 | 触发条件示例 | 响应时效 | 通知方式 |
|---|---|---|---|
| P0 致命 | 链接池积压>1万、Kafka 积压>10万、账号池水位<10%、调度中心宕机 | < 5 分钟 | 电话 + IM + 邮件 |
| P1 严重 | 某平台成功率<70%、ES 磁盘>85%、链接消费停滞 | < 15 分钟 | IM + 邮件 |
| P2 警告 | 单平台成功率<90%、Lag 持续上升、入池去重率异常 | < 1 小时 | IM |
| P3 提示 | 慢查询增多、Pod 偶发重启 | 日报 | 日报汇总 |

### 2.5 核心监控大盘

```text
大盘1 总览仪表盘：链接池水位 / 全平台成功率 / 端到端延迟 / 资源水位
大盘2 链接池盘：  入池/消费速率、按来源分布、消费延迟、积压趋势 ⭐新增
大盘3 平台维度盘：按 TikTok / X / FB / TG 拆分的成功率与封禁率
大盘4 资源池盘：  账号/IP/Cookie 三池水位曲线 + 预警线
大盘5 质量看板：  去重命中率（入池+入库双层）/ 校验失败率 / 死信积压
大盘6 调度看板：  链接领取延迟 / 优先级分布 / 重试率
```

### 2.6 关键能力清单

```text
1. 系统指标 + 业务指标双覆盖（链接池指标 + 业务指标优先）
2. P0~P3 四级告警分级与差异化路由
3. 告警抑制与聚合（避免风暴）
4. SLO 定义（如链接入池→落地 P99 < 10min）
5. 历史指标长期存储（用于容量规划与复盘）
6. 链接级全链路 trace（入池→调度→抓取→入库可追踪）
```

## ③ P0-3：数据质量与去重机制设计

### 3.1 双层去重架构（因链接驱动而强化）

链接驱动模式下，去重分**两层**执行，互相补充：

```text
第一层：入池去重（URL 级）—— 在链接池环节，见 1.2
  作用：同一 URL 不重复抓取，从源头节省资源
  时机：链接注入链接池时

第二层：入库去重（内容指纹级）—— 在 ETL 环节，见 3.2
  作用：不同 URL 指向相同/近似内容（转载、搬运、改写）去重
  时机：抓取内容入库时
```

### 3.2 入库去重策略（三层指纹）

```text
第一层：精确去重（URL / 平台主键 ID）
  存储：Redis Set / BloomFilter（高频判断）
  粒度：同一条内容绝对去重

第二层：内容指纹去重（SimHash，64 位）
  适用：转载、搬运、轻微改写的近似内容
  规则：Hamming 距离 ≤ 3 视为重复，仅保留首发版本
  存储：HBase（指纹倒排索引）

第三层：语义去重（MinHash + LSH，可选）
  适用：跨语言、跨平台的同源情报聚合
  规则：Jaccard 相似度 ≥ 0.85 聚合为同一事件
```

### 3.3 数据质量校验规则

校验在 ETL 管道内**串行执行**，任一规则失败则数据进入隔离区（不入主库）：

```text
1. Schema 校验：字段完整性、类型、必填项（如 platform / author_id / content / timestamp）
2. 时间合理性：发布时间不早于平台成立日、不晚于当前时间
3. 内容有效性：正文非空、长度在合理区间、非纯表情/乱码
4. 数值边界：转发/评论/点赞数 ≥ 0 且不超过合理上限
5. 平台一致性：账号 ID 格式符合该平台规范
6. 异常检测（统计模型）：
   - 单账号短时高频发布 → 疑似机器人/水军
   - 内容相似度突增 → 疑似协同行动（认知战关键信号）
   - 地理/语言分布异常 → 疑似伪造
```

### 3.4 质量处理流水线

```mermaid
flowchart TB
    RAW["爬虫抓取的原始数据"] --> FP{"入库指纹去重<br/>SimHash"}
    FP -->|"重复"| DROP["丢弃<br/>计入去重指标"]
    FP -->|"不重复"| SC{"Schema 校验"}
    SC -->|"失败"| ISO[("隔离区 dirty_zone<br/>OSS")]
    SC -->|"通过"| BIZ{"业务规则校验"}
    BIZ -->|"失败"| ISO
    BIZ -->|"通过"| ANO{"异常检测"}
    ANO -->|"可疑"| MARK["标记 suspicious=true<br/>入库但隔离分析"]
    ANO -->|"正常"| DB[("入主库<br/>PG / HBase")]
    MARK --> DB
    DB --> CHECK["人工抽检<br/>每日 0.1% 抽样复核"]
    CHECK -.->|"校准规则"| SC
```

### 3.5 数据血缘与可追溯

链接驱动模式下，血缘追溯**天然完整**——每条数据都能回溯到注入的链接：

```text
每条数据必带字段：
  - source_link_id     来源链接 ID（关联链接池）
  - source_url         原始 URL
  - link_source_type   链接来源（manual/recon/tactic）
  - link_source_ref    链接注入方（战法ID/分析师账号）
  - crawl_task_id      采集任务 ID（关联调度中心）
  - crawl_pod          采集节点
  - crawl_account_id   使用的账号（关联账号池）
  - crawl_proxy_ip     使用的代理 IP
  - raw_payload_url    原始报文存档地址（OSS）
  - quality_score      质量评分
  - dedup_fingerprint  去重指纹
```

出现情报争议时，可凭上述字段**完整回溯**：谁注入了链接 → 何时调度 → 哪个节点/账号抓取 → 如何入库——满足认知战情报的**可审计性**要求。

### 3.6 关键能力清单

```text
1. 双层去重（入池 URL 级 + 入库内容指纹级）
2. 三层入库指纹（精确 + SimHash + 语义）
3. 六类质量校验规则（Schema + 业务 + 异常检测）
4. 脏数据隔离区（不污染主库，可复盘）
5. 人工抽检闭环（规则持续校准）
6. 链接到入库全字段血缘（满足情报可审计性）
7. 质量指标上报监控大盘（与 P0-2 联动）
```

## 4. P0 三件套协同关系

三个 P0 模块以**链接池**为枢纽，构成自我调节的闭环：

```mermaid
flowchart LR
    LP[("链接池<br/>外部维护注入")]
    MON["② 监控告警<br/>链接池水位/成功率/质量指标"]
    SCH["① 调度中心<br/>链接池积压→扩消费并发<br/>账号水位低→降并发<br/>成功率低→切换平台"]
    CRAWL["爬虫集群<br/>消费链接抓取内容"]
    QUAL["③ 质量与去重<br/>双层去重+校验<br/>脏数据隔离，质量打分"]

    LP -->|"消费链接"| SCH
    MON -.->|"反馈调节"| SCH
    SCH -->|"下发抓取任务"| CRAWL
    CRAWL --> QUAL
    QUAL -->|"质量指标回流"| MON
    MON -.->|"链接池水位反馈"| LP
```

**协同价值：**
- **链接池**是输入闸门，由外部维护，爬虫只消费
- 调度中心根据**监控指标**动态调节消费速率（如封禁率升高则降速）
- 质量模块把**去重命中率、校验失败率**上报监控，异常时触发告警
- 监控告警为调度提供**反馈信号**，形成自适应系统

## 5. 落地优先级与里程碑

| 阶段 | 周期 | 交付内容 | 验收标准 |
|---|---|---|---|
| 阶段 0 | 第 1-2 周 | 链接池 + 调度 MVP（注入 API + 优先级消费 + 状态机） | 链接可注入、可去重、可续爬 |
| 阶段 1 | 第 3-4 周 | 监控告警 MVP（Prometheus + 链接池/业务指标） | P0 告警 5 分钟内触达 |
| 阶段 2 | 第 5-6 周 | 入库去重 + Schema 校验 + 隔离区 | 脏数据零落库，重复率<1% |
| 阶段 3 | 第 7-8 周 | 三模块联动 + 异常检测 + 数据血缘 | 闭环可用，链接→入库可追溯 |

---

## 6. 一句话总结

> 采集范式从"定时巡采"转为**"链接驱动"**：链接由外部程序/人工维护并注入**链接池**，爬虫作为执行器消费链接、定向抓取。
> P0 三件套——**链接池+调度（大脑）、监控（眼睛）、质量去重（免疫系统）**——让系统"扛打、可信、可控、可审计"，这正是认知作战定向情报采集的基本要求。

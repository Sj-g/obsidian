# Linear Issue 规范

## 一、标题格式

**结构：`【类型】动词 + 对象 + 限定语`**

- 全角 `【】`，前缀紧跟标题不加空格
- 前缀后用动词打头，说明动作类型
- 一行内写完，前 3 个词即可判断意图
- 不写用户故事（如"作为用户，我希望…"）
- 不写模糊词（"优化一下""处理某问题"）
- 不重复 Label/项目已表达的信息

### 类型前缀词表（封闭，勿随意扩充）

| 前缀      | 含义           | 示例                    |
| ------- | ------------ | --------------------- |
| `【功能】`  | 新功能开发        | 【功能】新增 Google 第三方登录   |
| `【Bug】` | 缺陷修复         | 【Bug】修复日历加载白屏         |
| `【优化】`  | 已有功能改进       | 【优化】首页首屏加载降至 2s       |
| `【重构】`  | 内部调整不改行为     | 【重构】统一支付模块错误处理        |
| `【调研】`  | 探索 / 方案未定    | 【调研】评估 WebSocket 替换轮询 |
| `【运维】`  | 部署 / 配置 / 依赖 | 【运维】升级 Node 至 20 LTS  |
| `【文档】`  | 文档类          | 【文档】补充登录接口说明          |
| 【验证】    | 验证类          | 【验证】验证开源项目技术栈         |
| 【设计】    | 设计类          |                       |
| 待定      |              |                       |

### 动词表

新增 / 修复 / 优化 / 重构 / 移除 / 调研 / 更新

## 二、描述格式

**原则：描述可选，只写执行任务所需的必要信息；用户反馈直接引用原话并附链接。**

### 功能模板
```
## 背景
一句话说明动机，或引用需求来源链接

## 验收标准
- [ ] 可衡量的完成条件 1
- [ ] 可衡量的完成条件 2

## 备注
设计稿 / 技术方案 / 相关 issue 链接

```


### Bug 模板

```
## 现象
发生了什么

## 复现步骤
1.
2.

## 期望 vs 实际
- 期望：
- 实际：

## 环境 / 链接
版本 / 日志 / Sentry 链接
```

### 调研模板
```
## 要回答的问题
xxxx
## 备选方案
- 方案 A：
- 方案 B：

## 结论 / 建议
（调研完成后填写）
```

## 三、子 Issue 规范

**何时拆：工作大于单个 issue、小于一个 project 时；或需多人协作时。**
（若父 issue 大到接近项目规模，改用「转为项目」）

- 子 issue 命名可假设父 issue 上下文已知，用 `【阶段】` 前缀按流程拆分
- 每个子 issue 仍是"动词 + 对象"，可独立指派

### 阶段前缀

`【设计】` `【前端】` `【后端】` `【测试】` `【联调】` `【上线】`

### 示例

【功能】新增 Google 第三方登录
  ├── 【设计】登录按钮与授权流程 UI
  ├── 【后端】接入 OAuth 回调接口
  ├── 【前端】对接登录状态存储
  └── 【测试】补充异常与埋点用例

## 四、字段与协作

- **类型 / 模块** → 用 Label（可筛选、可统计、带颜色）
- **紧急度** → 用 Priority 字段，尽量不放进标题
- **谁执行谁写 issue**；代他人报 Bug 时先写成"请求 / 问题描述"，再由受理人改写为任务
- 团队设置开启：**所有子 issue 完成 → 父 issue 自动完成**

---

## 五、硬性规则

1. 统一全角 `【】`，禁止混用 `[]`、`「」`
2. 前缀词表封闭，新增需团队约定
3. 一个标题最多 1 个类型前缀（`【紧急】`除外）
4. 能用 Label / Priority 表达的，不放进标题
5. 标题 = `【类型】动词 + 对象`；同时打对应 Label + 设置 Priority

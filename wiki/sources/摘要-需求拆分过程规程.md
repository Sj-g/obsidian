## 核心摘要
本资料是一份基于 [[GJB438C]] 的《需求分析与需求拆分过程规程》V1.0，定位为"供智能体执行的提示词规范"。它规定了一条从模糊大需求（Epic）到可独立交付、可验证用户故事的完整流水线：需求真伪辨别 → 本质锁定 → 三层次校验 → 价值评估 → 可行性判定门 → 影响地图 → 用户故事地图 → 验收标准 → INVEST 标尺 → 纵向拆分 → 依赖解耦 → 交付验证反馈。规程强调强制判定门、纵向切蛋糕、MVP 小步快跑，并附 11 条智能体执行约束。

## 关键信息
**规程骨架（12 个活动产出物）：**
收集需求(需求池) → 辨别真伪(5Why) → 影响地图 → 三层次校验 → 价值评估(KANO/RICE) → 可行性判定门(通过/降级/否决) → 用户故事地图 → 纵向拆分并划MVP → 依赖识别与解耦 → 细化验收标准 → 输出文档评审排期 → 交付验证(数据/功能反馈回溯)。

**引用的方法论/模型：**
- [[需求分析与拆分]] — 本规程的统领主题
- [[INVEST准则]] — 用户故事质量标尺（独立/可协商/有价值/可估算/小/可测试）
- [[影响地图]] — Why-Who-How-What 保证功能可回溯业务价值
- [[需求优先级评估]] — KANO（基本/期望/兴奋型）+ RICE（触达×影响×信心÷成本）
- [[纵向拆分]] — 切蛋糕 vs 横向千层饼
- [[MVP]] — 最小可行产品，首发可验证闭环

**判定门三态：** 通过（进入故事地图）/ 降级（退回需求池标注触发条件）/ 否决（归档记录理由）。未过判定门禁止进入拆分。

**核心反模式（误区）：** 把解决方案当需求、横向千层饼拆分、跳过价值与可行性评估、故事刚拆出即锁死验收标准、忽视依赖、技术需求硬套切蛋糕、一次想做全、反馈只改功能不验假设。
